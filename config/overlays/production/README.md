# Production overlay — Patch assistant

A reviewed-render, GitOps-applied production deployment of the assistant. It is
**not** a one-shot `kubectl apply` target: it references Secrets and hostnames
you supply, and it deliberately pins nothing to a mutable dev image.

```bash
kubectl kustomize config/overlays/production   # render + review, then apply via CD
```

## What it deploys (namespace `patch-system`)

- The assistant Deployment (3 replicas, HPA 3–12, PDB minAvailable 2), hardened:
  non-root, read-only rootfs, dropped capabilities, seccomp RuntimeDefault.
- Readiness gated on dependency reachability (`/readyz`), liveness bare
  (`/healthz`). `/metrics` and the probes are **not** exposed publicly — the
  HTTPRoute publishes only `/a2a` and `/.well-known`.
- A 3-instance CloudNativePG cluster with continuous backup (PITR) for the
  conversation **and** durable task store.
- TLS ingress via a Gateway-API Gateway + HTTPRoute + cert-manager Certificate.
- A default-deny NetworkPolicy with explicit egress to DNS, Postgres, and the
  in-cluster platform endpoints.

## Posture vs. dev

| | dev overlays | production |
|---|---|---|
| AuthN | dev tokens | **OIDC** |
| AuthZ | claims (trust the token) | **SubjectAccessReview** against Milo |
| Capabilities | fixture file | **catalog** provider API |
| Model | in-cluster stub | real model via the AI gateway (keyless) |
| Store | single Postgres | **3-instance CNPG + backup/PITR** |
| Ingress | port-forward, plaintext | **TLS** at a Gateway |
| Config safety | dev values allowed | boots only if the posture validates |

## Placeholders to substitute (search `REPLACE_WITH_`)

- `kustomization.yaml`: image tag/digest, `PUBLIC_BASE_URL`, `GATEWAY_URL`,
  `GATEWAY_MODEL`, `CAPABILITY_PROVIDER_URL`.
- `cnpg-cluster.yaml`: storage class, backup bucket / object-store provider.
- `gateway-tls.yaml`: public hostname, `ClusterIssuer`, `GatewayClass`.
- `networkpolicy.yaml`: the ingress namespace that fronts external traffic.

## Secrets the operator creates out-of-band (NEVER committed)

Create these in `patch-system` before/with the deploy:

```bash
# OIDC verification settings
kubectl -n patch-system create secret generic assistant-oidc \
  --from-literal=issuer=https://<your-issuer> \
  --from-literal=audience=<your-audience> \
  --from-literal=projectsClaim=projects

# Usage-metering collector (billing pipeline provides durability downstream)
kubectl -n patch-system create secret generic assistant-usage-collector \
  --from-literal=url=https://<collector-host> \
  --from-literal=apiKey=<collector-key>

# Object-store credentials for CNPG backups (match your provider block)
kubectl -n patch-system create secret generic conversation-store-backup \
  --from-literal=ACCESS_KEY_ID=<...> --from-literal=SECRET_ACCESS_KEY=<...>
```

`conversation-store-app` (the DB DSN) and `assistant-tls` (the served cert) are
generated by the CloudNativePG operator and cert-manager respectively — you do
not create them.

## Authorization (SubjectAccessReview)

`AUTHZ_MODE=sar` makes the assistant call SubjectAccessReview against the Milo
control plane before acting on a project (fail-closed, short allow-cache).
By default it uses the pod's own service-account token + the in-cluster API
endpoint; grant that service account permission to issue SARs
(`authorization.k8s.io/subjectaccessreviews: create`) via RBAC in your platform.
For an external control plane, set `AUTHZ_SAR_API_URL` / `AUTHZ_SAR_TOKEN_PATH`
/ `AUTHZ_SAR_CA_CERT_PATH` and the resource-attribute overrides.

## Known follow-ups

- **Untrusted-provider SSRF posture**: the overlay sets
  `CAPABILITY_ALLOW_PRIVATE_NETWORKS=true` (correct while providers are the
  trusted catalog). The guard supports a host allow-list for untrusted
  third-party providers, but it is not yet config-wired — wire
  `CAPABILITY_ALLOW_HOSTS` / `CAPABILITY_ALLOW_CIDRS` before onboarding
  untrusted providers.
- **RBAC + ServiceAccount** for the SAR caller are environment-specific and not
  included here.
